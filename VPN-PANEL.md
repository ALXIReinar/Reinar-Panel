## 3. Шаблоны

Вкладка эндпоинтов в Swagger - `Proto Templates`

Эндпоинт - GET `/api/v1/private/templates/all`. Рекомендуется прочесть его докстринг в сваггере. Отдаёт
```
{
    "templates": [
        {...},
        {...}
    ],
    "spec_params": [
      {
        "id": 1,
        "key": "pbk",
        "tmp_id": 1
      },
      {
        "id": 2,
        "key": "flow",
        "tmp_id": 1
      }
    ]
}
```

Тоже контейнер. Каждая строчка - превью шаблона, отображаем основные параметры

### Столбцы для отображения

`| id | title | url_tmp | status | proto_python_lib |`

`id` - он же `tmp_id`

`url_tmp` - Заморочистое поле. Нужна обработка с использованием 

`spec_params`. В этой `url_tmp` есть плейсхолдеры {{key___val}}, {{custom_key}} - те самые `spec_params` их нужно подсвечивать. 

`status` - 1 или 2. Системный/Пользовательский. Системный нельзя редактировать, только дублировать

### Столбцы для апи

`| id | ['spec_params']['id'] |`

`['spec_params']['id']` - он же `key_id`

### Функции

- Пагинация cursor-based
- Дублирование шаблона(с помощью 2х ручек - добавление и обновление). При обновлении просто подставить все параметры копирумеого шаблона
- Создание
- Удаление
- Обновление - эндпоинт, используемый для редактора всего, что только принадлежит шаблону

## 3.1. Расширенная шаблона

Тут и начинается история с редактором

эндпоинт для получения всех параметров шаблона - GET `/api/v1/private/templates/by_id`
Эндпоинт для внесения изменений пользователя - PUT `/api/v1/private/templates/update`

```
 N8N подход!
 При работе в редакторе можно подгрузить конфиг файл. Он распарсится на ключи-блоки, которые пользователь будет просто перетягивать в редактор

 P.S. Функции подгрузки файла и его парсинг пока не разработаны
```
- От бэка необходим функционал сохранения файлов, по которым пользователь хочет составлять конфиг ссылку. Классический CRUD для удаления, добавления, чтения, обновления в рилтайме
- Парсинг джсона в блоки, перетяжка блоков - осуществляется на фронте

### Плейсхолдеры в шаблон-ссылке

Делятся на служебные и на
Остальные
 - Файловые (Формируются по flatten-json key из конфиг файла)
 - Кастомные (не лежат в файле, задаются пользователем под каждую виртуальную ноду)

#### Служебные

Ограничены одинарными фигурными скобками, используются в исходном коде. 

Обязательным является только 
- `{user_uuid}` - подставляется в ссылку в самый последний момент, при выдаче ссылки пользователю
- 

Другие обязательные, но не критичные
- `{{node___address}}` - **Двойные фигурки**. Но используется в исходном коде. Подставляет публичный ip или домен сервера
- `{{node___title}}` - Название локации в впн-клиенте пользователя

```
Почему не критично? 
- Библиотека для рендера при конфликте, бракованные или неправильные плейсхолдеры молча съедает. 
- Вместо {{bad_placeholder}} в шаблон подставится '' - пустая строка
```

P.S: Возможно, для них можно оставить `_` вместо тройного подчёркивания. 

## 3.2. Редактор джсон объектов пользователей

## 4. Spec params для шаблонов

Это **редактор** для кастомных плейсхолдеров в шаблонах. Максимально близко похож на редактор джсон объектов пользователей

**Кастомные плейсхолдеры** - позволяют задавать и использовать в шаблоне значения, которых нет в конфиг-файле. Например - публичный ключ для vless

Эндпоинт - GET `/api/v1/private/templates/specs/vnode/get_spec_values`

- Отдаёт пачку ключей (spec_key_id, key_name) - привязаны к **шаблону**
- Пачку значений (value_id, value) - привязаны к **ключам** и **виртуальным нодам**

#### Логически два редактора - Для ключей и для значений

> PUT - `/api/v1/private/templates/specs/set_keys`

Для ключей. Совмещает в себе add, update, delete - В эндпоинт прокидывается **текущее состояние** кастомных ключей

> PUT `/api/v1/private/templates/specs/vnode/set_key_values`

Для значений. Тоже add, delete, update. Но для значений. Требует айди ключей и айди виртуальной ноды

## 5. Физические ноды (Серверы)

### Столбцы для отображения

| id | ip | private_ip | api_port | title | created_at | updated_at | is_active | binded_vnodes_count |


`is_active` - визуально выделять (зелёный/серый индикатор)
`api_port` - Порт нод клиента

### Столбцы для апи

| id |

### Создание физической ноды

Эндпоинт - POST `/api/v1/private/nodes/create`

**Особенность:** При создании автоматически происходит ping-проверка по адресу `http://{private_ip}:{api_port}/ping`. Если нода не отвечает или отвечает некорректно - создание отклоняется с ошибкой 502/400.

**Поля для создания:**
- `ip` - публичный IP, обязателен
- `private_ip` - приватный IP для WireGuard, обязателен 
- `api_port` - порт Node Client API, обязателен
- `title` - название ноды, обязательно
- `is_active` - вкл/выкл (по умолчанию true)

## 6. Команды протоколов

Вкладка эндпоинтов в Swagger - `Proto Commands`

Управление командами, которые выполняются на сервере для конкретного протокола. Команды используются для взаимодействия с ядром протокола на разных этапах работы.

Эндпоинт - GET `/api/v1/private/protocol-commands/by_proto/{proto_id}`

### Отображение в UI

- Настройка этого блока отвечает за горячие функции над протоколом. Например, перезагрузка ядра, выключение, запуск и т.п.
- Для удобства каждая команда - кнопка в расширенной странице виртуальной ноды
- Можно подумать, чтобы для этих команд можно было выбрать иконки(Или же просто пользователю подсказывать, мол, ты можешь смайлики поставить для красоты)
- Это можно представить в окне виртуальной ноды как выпадающий список, рядом поставить "▶️" для исполнения этой команды на нод клиенте. (POST `/api/v1/private/cmd_center/remote_execute`)

### Функции

1. Получение всех команд для конкретного протокола
2. Массовая вставка команд (bulk insert)
3. Массовое обновление команд (bulk update)
4. Массовое удаление команд (bulk delete)

### Столбцы для отображения

| cmd_id | title | command | created_at |

`title` - название команды (например, "Добавить пользователя", "Перезапустить ядро")

`command` - CLI команда для выполнения на сервере

### Столбцы для апи

| id | proto_id |

### Массовая вставка команд

Эндпоинт - POST `/api/v1/private/protocol-commands/bulk/insert`

**Особенность:** Позволяет добавить сразу несколько команд к протоколу одним запросом.

**Поля:**
- `proto_id` - ID протокола (обязательно)
- `commands` - массив объектов команд (минимум 1):
  - `cmd_title` - название команды (1-200 символов, обязательно)
  - `command` - CLI команда (минимум 1 символ, обязательно)

**Возвращает:** Массив ID созданных команд

### Массовое обновление команд

Эндпоинт - PUT `/api/v1/private/protocol-commands/bulk/update`

**Поля:**
- `proto_id` - ID протокола (обязательно)
- `commands` - массив объектов для обновления (минимум 1):
  - `id` - ID команды (обязательно)
  - `cmd_title` - новое название команды (1-200 символов, обязательно)
  - `command` - новая CLI команда (минимум 1 символ, обязательно)

**Возвращает:** Количество обновлённых команд

### Массовое удаление команд

Эндпоинт - DELETE `/api/v1/private/protocol-commands/bulk/delete`

**Поля:**
- `proto_id` - ID протокола (обязательно)
- `cmd_ids` - массив ID команд для удаления (минимум 1)

**Возвращает:** Количество удалённых команд

## 7. Белый список команд (Whitelist)

Вкладка эндпоинтов в Swagger - `Whitelist Management`

Управление белым списком команд для удалённого выполнения на серверах. Только команды из белого списка могут быть выполнены через *Remote Command Execution*. Используется Redis кэширование для оптимизации производительности.

Эндпоинт - GET `/api/v1/private/whitelist/all`

### Функции

1. Получение всех базовых команд whitelist
2. Массовое обновление статусов команд (bulk update - активация/деактивация)
3. Массовое добавление команд (bulk add)
4. Массовое удаление команд (bulk delete)

### Столбцы для отображения

| id | command | is_active |

`command` - текстовое представление команды. Белый список настроен на **базовые команды**. 
- Например `ls`. Это значит, любые вариации аргументов с этой командой будут работать. 
- Проверка команды из белого списка работает через `in`, **не по равенству** `input_command` и `wh_list_command`

`is_active` - визуально выделять (активна/неактивна). Только активные команды разрешены к выполнению

### Столбцы для апи

| id |

### Массовое обновление статусов

Эндпоинт - PUT `/api/v1/private/whitelist/bulk_update`

**Особенность:** 
1. Автоматически инвалидирует кэш Redis после обновления.
2. **Если в белом списке нет ни одной активной команды, значит он выключен** => любая команда будет пропущена. 
3. НО валидация в **API** производится всегда(для защиты от опасных паттернов и команд)

**Поля:**
- `set_as_active` - массив ID команд для активации (по умолчанию [])
- `set_as_inactive` - массив ID команд для деактивации (по умолчанию [])

**Возвращает:** Количество активированных и деактивированных команд

### Массовое добавление команд

Эндпоинт - POST `/api/v1/private/whitelist/bulk_add`

**Особенность:** 
- Дубликаты команд игнорируются (unique constraint)
- При частичной вставке возвращает код 202 и список успешно добавленных команд

**Поля:**
- `commands` - массив строк с командами (обязательно)

**Возвращает:** 
- Код 200 + ID созданных команд (если все добавлены)
- Код 202 + ID успешно добавленных команд (если были дубликаты)

### Массовое удаление команд

Эндпоинт - DELETE `/api/v1/private/whitelist/bulk_delete`

**Поля:**
- `ids` - массив ID команд для удаления (обязательно)

**Возвращает:** Сообщение об успешном удалении

### Примечания

- Все write-операции автоматически очищают Redis кэш командами `flush_whitelist`
- При первом запросе `/all` кэш создаётся автоматически, если отсутствует
- Whitelist используется для контроля безопасности удалённого выполнения команд


## 8. Удалённое управление нод-клиентами

Вкладка эндпоинтов в Swagger - `Command Center Admin2Node`

Удалённое управление нодами: выполнение команд, редактирование конфиг-файлов, ручное управление пользователями на ядрах протоколов. Включает проверку безопасности и валидацию через whitelist.

**В данном разделе "правило заголовка второго уровня" нарушается**. В каждом заголовке я отметил "Функция" или "Отд. Раздел"

### 8.1. Функция: Удалённое выполнение команд



Эндпоинт - POST `/api/v1/private/cmd_center/remote_execute`

**Функции:**
1. Выполнение CLI команд на удалённых серверах
2. Поддержка **whitelist**
3. Фиксация всех **cmd-execute** в историю выполнения

**Поля, все обязательны:**
- `node_proto_id` - ID виртуальной ноды
- `private_ip` - приватный IP ноды
- `api_port`
- `cmd` - команда для выполнения. Может быть как **произвольная**(введена пользователем), так и из `Proto Commands`

**Ошибки:**
- 422 - валидация команды не прошла. Команда не в белом списке
- 400 - Ошибка исполнения на ноде
- 500 - Ошибка на админке

### 8.2.1. Отд. Раздел: Редактор конфиг-файлов впн-ядер

Редактор для работы с конфигурационными файлами протоколов на удалённых нодах.

#### Чтение конфига

Эндпоинт - GET `/api/v1/private/cmd_center/config_file/read`

**Query параметры:**
- `node_proto_id` - ID виртуальной ноды (обязательно). **По нему вытягивается путь к конфиг-файлу**. Так любой файл, кроме конфиг-файла, прочесть сложнее
- `flatten_json_users_key` - ключ к списку пользователей в JSON (опционально). При чтении этот объект <u>может</u> вырезаться для:
  - оптимизации трафика
  - конфиденциальности пользовательских данных
  - Чтобы не снести всех пользователей из ядра

**Возвращает:**
- `file_content` - содержимое файла

#### Запись конфига

Эндпоинт - PUT `/api/v1/private/cmd_center/config_file/write`

**Поля:**
- `node_proto_id` - ID виртуальной ноды (обязательно). Аналогично `/read` эндпоинту
- `file_content` - содержимое файла (обязательно)
- `flatten_json_users_key` - ключ к списку пользователей (опционально). При записи этот объект переносится из старого файла

**Особенности:**
- Автоматически использует `config_path` из настроек виртуальной ноды
- После записи **администратору** нужно перезагрузить ядро протокола для применения изменений. 

P.S: Есть смысл настроить галочку "Перезапустить ядро" при записи + настроить бинд команды для перезагрузки

**Ошибки:**
- 404 - Виртуальная нода не найдена
- 400 - Путь к конфиг-файлу не указан
- 500 - Ошибка выполнения

## 9. Тарифные планы (Группы подписок)

Вкладка эндпоинтов в Swagger - `Subscription Plans`

Управление тарифными планами и привязка виртуальных нод к планам. Каждый план определяет набор серверов (виртуальных нод), доступных пользователям по подписке.

Эндпоинт для списка - GET `/api/v1/private/subscriptions/plans/all`

### Функции

1. Создание (достаточно названия, основная настройка через update)
2. Получение всех планов + offset/limit пагинация
3. Получение конкретного плана с привязанными виртуальными нодами(локации в впн клиенте юзера)
4. Обновление плана и управление связями с виртуальными нодами(локации в впн клиенте юзера)
5. Удаление плана

### UI Отображение

Эндпоинт - GET `/api/v1/private/subscriptions/plans/all`

Впервые не контейнер-таблица; Контейнер с карточками. `/all` отдаёт именно такой набор, который приятно будет смотреться в элементе-карточке

### Столбцы для отображения

| id | title | description | ttl_days | cost | traffic_limit_day | is_active |

`title` - название плана (например, "Базовый", "Премиум")

`ttl_days` - длительность подписки в днях

`cost` - стоимость в копейках

`traffic_limit_day` - лимит трафика в МБ (-1 = безлимит). 
- P.S: На данный момент безлимит не реализован, его косвенно можно добиться, указав петабайт данных как лимит на день

`is_active` - визуально выделять (активен/неактивен)

### Столбцы для апи

| id |

### Создание плана

Эндпоинт - POST `/api/v1/private/subscriptions/plans/create`

**Поля:**
- `title` - название группы (1-128 символов, обязательно)

**Возвращает:**
- `plan` - ID созданного плана

**Ошибки:**
- 409 - План с таким названием уже существует

### Расширенная тарифного плана

**Эндпоинт данных** - GET `/api/v1/private/subscriptions/plans/get/{plan_id}`

**Возвращает:**
- Детальную информацию о плане
- `vnodes` - список привязанных виртуальных нод

**Ошибки:**
- 404 - План не найден

**Эндпоинт редактирования** - PUT `/api/v1/private/subscriptions/plans/update`


**Поля (все опциональные):**
- `id` - ID группы (обязательно)
- `title` - название (1-128 символов)
- `description` - описание
- `ttl_days` - длительность в днях (> 0)
- `cost` - стоимость в копейках (≥ 0)
- `traffic_limit_day` - лимит трафика в МБ (≥ -1, где -1 = безлимит)
- `is_active` - статус активности
- `add_node_proto_ids` - массив ID виртуальных нод для привязки
- `remove_node_proto_ids` - массив ID виртуальных нод для отвязки

**Возвращает:**
- `success` - статус операции
- `attache_res` - результат привязки нод (status_code, attached_msg)
- `detach_res` - результат отвязки нод (status_code, detach_message)

**Ошибки:**
- 404 - План не найден (если не переданы списки нод)

### Удаление плана

Эндпоинт - DELETE `/api/v1/private/subscriptions/plans/delete`

**Особенность:** CASCADE удаляет все связи с виртуальными нодами.

**Поля:**
- `id` - ID группы (обязательно)

**Возвращает:**
- `success` - статус удаления

## 10. История Remote Execute команд

Создана "наотвали", но даже так её польза будет неоценима

GET - `/api/v1/private/cmd_center/history/all`

**Функции**
- curdsor-based пагинация
- Сортировка по id (по времени - старые/новые)

**Примечание** - Это тоже таблица-контейнер. НО необходимо, чтобы каждое поле можно было удобно рассмотреть в "полном объёме". Значения могут быть весьма большими

3. failed_on_node

**Столбцы для апи**
- id - для cursor-based пагинации
