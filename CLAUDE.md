## О проекте

Универсальная VPN-панель: поддерживает любые ядра и протоколы через **шаблоны**. Каждая процедура,
которой нужна особая обработка под ядро, берёт скрипт из шаблона; скрипт выполняется в
изолированной песочнице и отдаёт результат в админку.

Платформа находится в стадии разработки. У неё нет пользователей(ни VPN-провайдеров, ни пользователей самих услуг VPN).
Поэтому поддержка рассматривается только для `Ubuntu 22.04`. Для нужд разработки есть зарубежный VDS сервер(тестовый стенд). 
На нём развёрнута VPN-панель(`web`, `arq_worker`, `sub`, `node_client`).

- **Шаблон** — набор скриптов для одной вариации протокола (`xray-vless-reality-tcp` и
  `xray-vless-reality-grpc` — разные шаблоны). Имя: ядро-протокол-параметры через `-`.
- **VPN-ядро** — бинарник на сервере (xray, sing-box, amneziawg…).
- **Инстанс ядра** — запущенный экземпляр, например `xray run -c /configs/vless-reality-tcp.json`.
- **Физическая нода** — сервер с установленным `node_client`, который управляет инстансами.
- **Виртуальная нода** — инстанс ядра, зарегистрированный в панели. На физической ноде их сколько угодно.

## Работа с Git. Ветки

Описание, что и в каких ветках происходит. Жёсткие правила ведения и интеграции только для **main**,
относительно жёсткие на **dev/master** и рекомендованные правила для всех остальных **dev веток**. 
**Feature** ветки определённым сводом правил не преследуются

1. `main` - релизная, предполагается для использования VPN-провайдерами. Полностью зелёный CI/CD в ПР
2. `dev/master` - аналог main ветки для разработчиков фронт и бек части(что-то вроде альфа/бета тестирования). Допускаются ПР с красными CI/CD
3. `dev/backend` - ветка бекенд разработки, на которой можно работать по всем микросервисам сразу
4. `dev/frontend` - ветка фронтенд части
5. `dev/node` - ветка разработки `node_client`
6. `dev/bot` - ветка разработки `bot`
7. `deb/sub` - ветка разработки `sub`

## Структура

Монорепозиторий, Python 3.12, общее окружение `.venv` в корне.

| Сервис | Каталог | Что это |
|---|---|---|
| `web` | `web/` | админка (FastAPI) |
| `sub` | `web/sub/` | сервис подписок |
| `arq_worker` | `web/arq_worker/` | фоновые задачи (arq) |
| `bot` | `bot/` | Telegram-бот |
| `node_client` | `node_client/` | агент на физической ноде |

Миграции — Alembic в `web/alembic`.

Эндпоинты и SQL пишутся по скиллам `fastapi-endpoint` и `sql-queries`. Что отличает сервис
(зависимости `XxxDep`, авторизация, импорт `log_event`, куда подключать роутер) — в его карточке:
`web/api/CLAUDE.md`, `web/sub/api/CLAUDE.md`, `node_client/api/CLAUDE.md`, `web/arq_worker/funcs/CLAUDE.md`.

## Окружение и команды

Работаем в Linux (WSL). Python проекта — `.venv/bin/python`. **Не используй**
`.venv/Scripts/*.exe` и не ищи python через PATH: всё запускается через `./run.py`, он сам
переключается на `.venv`.

```bash
./run.py <сервис> <путь_к_тестам> [аргументы pytest]   # путь — относительно каталога сервиса
./run.py <сервис> run [аргументы приложения]
./run.py check                                         # глубокая проверка изменённого кода
```

Примеры: `./run.py web tests/unit/test_jwt_factory.py -q`, `./run.py bot tests -q`,
`./run.py node_client tests/unit -q -k test_connection`.

Вывод тестов для агента сокращается (первые падения + сводка); полный лог —
`.claude/logs/pytest-<сервис>.log`, ищи в нём через grep, а не читай целиком.

Тесты `node_client` принимают `--mode real|mock` (по умолчанию `mock`; `real` поднимает
docker-контейнеры настоящих ядер) и `--protocol` — фильтр шаблонов: `xray-vless`, `singbox`, `"*"`
(все шаблоны из БД).

## Автоматические проверки (хуки)

Не запускай линтеры вручную после каждой правки — это делают хуки:

- **после каждой записи `.py`**: ruff сам форматирует файл и чинит безопасное; если в твоих правках
  остались ошибки (неопределённое имя, синтаксис, типовой баг), ты получишь их сразу;
- **после правки `.py` через Bash** (sed, heredoc, скрипт): те же замечания ruff, но без
  автоисправлений — поэтому код правь через Edit/Write;
- **в конце хода**: mypy, semgrep, pylint (сломанные и циклические импорты), vulture (мёртвый
  код) и ruff по строкам, которые ты менял.

Как реагировать:
- исправляй то, что относится к задаче;
- ложное срабатывание или проблему вне задачи не чини — назови её пользователю одной строкой с
  причиной. Хук не напоминает об одном замечании дважды;
- не глуши замечания (`# noqa`, `# type: ignore`, `# nosemgrep`) без объяснения в том же
  комментарии;
- старый код вне твоих правок не «причёсывай» без запроса.

## Как работать

- По умолчанию работай автономно в рамках запроса. Для большой задачи после короткой разведки
  обозначь цель, критерии готовности, ограничения и затрагиваемое окружение. Этот контракт можно
  взять из запроса и согласованной спеки (`.claude/specs/`, `.agents/specs/`, `.kiro/specs/`).
  Сообщи план и приступай, если рамки ясны. Порядок шагов можно менять по результатам проверки.
- Сначала проверяй факты по коду, документации, логам, БД и безопасным экспериментам.
  Локальные обратимые решения принимай сам. Существенные допущения фиксируй и отделяй от фактов.
  При расхождении со спекой сверяйся с её целью и действующим контрактом. Если меняется
  существенное требование, спроси и продолжай независимые части задачи.
- Запрашивай решение, когда оно существенно для продукта или архитектуры, дорого обратимо либо
  когда необходимые сведения недоступны. Запрашивай разрешение на выход за согласованный объём,
  необратимые действия и изменения общего окружения, если они ещё не разрешены. Назови
  рекомендуемый вариант, последствия и шаг, который зависит от ответа. Уже выданное разрешение
  действует в согласованных границах. Технические ограничения среды и явные контрольные точки
  задачи сохраняются.
- Новая логика и баги — через тесты: сначала падающий тест, потом код. Красный тест засчитывается,
  только если падает на проверке (`assert`, ожидаемое исключение) по той причине, которую ты ждал.
  Упал на `ImportError`, опечатке или фикстуре — это ещё не красный тест: почини и прогони снова.
- Баг не чинится с трёх попыток — четвёртую не делай. Опиши пользователю, что пробовал, что
  увидел и какие гипотезы остались: скорее всего, причина не там, где её ищешь.
- В конце большой задачи: прогони тесты затронутых сервисов (навык `/verify`).

## Как писать тесты

- Перед тестом назови поломку кода, которую он ловит (не та ветка/константа, нет побочного эффекта,
  не проверен пустой или чужой ввод). Не можешь назвать — тест не нужен или проверяет не то.
- Ожидаемое значение — литерал, посчитанный независимо, а не тем же кодом.
- Мокай только внешнюю границу (сеть, нод-клиент, очередь arq, время) и не проверяй сам мок; БД —
  тестовая, не мок. Проверяй поведение (ответ, строки в БД, вызов наружу), а не текст исходника.
- Код только для тестов — в фикстурах и `tests/`, не в рабочих классах.

- `postgresql` — dev-база. `test-postgresql` — тестовая, для написания и запуска тестов.
