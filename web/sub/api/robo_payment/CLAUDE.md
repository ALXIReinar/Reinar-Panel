# Платёжки в sub: адреса и rate-limit

Дополняет карточку `web/sub/api/CLAUDE.md`.

## Почему у платёжки свой сегмент

По смыслу это `/private`: оплату начинает только авторизованный пользователь. Но вебхук
провайдера приходит с его серверов, которые блокировать нельзя, — им нужен повышенный
rate-limit. Поэтому у **каждой** платёжной системы свой сегмент верхнего уровня, и reverse-proxy
выдаёт ему свою зону rate-limit:

| Провайдер | Сегмент | Роутер |
|---|---|---|
| RoboKassa | `/api/v1/robokassa` | `web/sub/api/robo_payment/payment_api.py` |
| YooKassa (пример на будущее) | `/api/v1/yookassa` | — |

## Новая платёжка или новый эндпоинт

1. Все эндпоинты провайдера — под его сегментом (`/api/v1/<провайдер>/...`). Сейчас у RoboKassa
   роутер с `prefix='/api/v1'`, а сегмент `/robokassa` повторён в путях
   (`/robokassa/get_pay_link`, `/robokassa/webhook`) — для новых платёжек сегмент — в `prefix`
   роутера.
2. В `web/sub/sub.caddy` — отдельный `handle /api/v1/<провайдер>/*` со своей зоной `rate_limit`
   (образец — блок «1.2 Маршрут для Робокассы»: `events 30`, `window 1s`). Без этого блока
   запрос снаружи уйдёт в раздачу SPA и до сервиса не дойдёт; если же вписать адрес в чужой
   `handle` (например, `/sub/*` с `events 20 / 60s`), вебхуки провайдера начнут получать 429.
3. Вебхук сверяет подпись провайдера до любых изменений в БД (у RoboKassa —
   `create_signature` в `handlers.py`, сравнение с ожидаемым хешем).
4. Время в платёжном API пока хранится без часового пояса (бэклог D6) — не усугубляй.
